# Styrene Contacts Page — Cross-Topology Address Consolidation

## Overview

A canonical Styrene Contacts page (served via the NomadNet page server) that consolidates a node's known addresses across all active transports — RNS destination hash, LXMF delivery hash, Yggdrasil address, I2P b32 address, web URL. Gives peers a single place to discover all the ways to reach a Styrene operator, regardless of which transport they arrived on. Feeds the i2p-address-book and makes cross-topology identity resolution more ergonomic.

## Research

### What gets consolidated

A Styrene operator may be reachable across multiple independent address spaces simultaneously:
- RNS destination hash (for LXMF chat, RPC, datalink)
- LXMF delivery destination hash (separate from the operator dest — peers sending via propagation need this)
- NomadNet destination hash (page server — may differ from above)
- Yggdrasil IPv6 address + port (WireGuard-over-Ygg or direct TCP)
- I2P b32 address (eepsite and/or SAM/streaming tunnel)
- Web URL (clearnet https:// presence, if declared)

Today, none of these are surfaced together. A peer who found you via NomadNet doesn't automatically know your LXMF hash. A peer who connected via Yggdrasil doesn't know your .b32.i2p. The node detail screen in the TUI shows some of these, but only for nodes already in the local mesh — there's no shareable, human-friendly format for "here's how to reach me."

The contacts page solves this: a single NomadNet page at `/page/contact.mu` (or `/page/index.mu` if no dedicated index) that lists all active transports with their addresses in copyable format, plus a "message me" lxmf@ link (which we now know works correctly in the TUI).

### Relationship to existing surfaces

- The page server already generates a NomadNet index page from templates in ~/.styrene/pages/. A contact.mu template can be auto-generated at daemon startup from the identity config + detected overlay addresses, same pattern as the existing index page generation.
- The /meta DirectLink response already returns b32_address, ygg_address, ygg_port, web_url. The contacts page is the human-readable version of /meta — same data, presented as a browsable NomadNet page rather than a JSON endpoint.
- The i2p-address-book feature needs a way for Styrene nodes to self-declare their eepsite addresses. A contacts page at a well-known path (/page/contact.mu) is the natural place to read this from — when the Hub indexes nodes for the address book, it can fetch /page/contact.mu from known nodes to extract their b32_address.
- The TUI Contacts screen already has a contact model (ContactService, contacts DB table). Cross-topology consolidation would enrich existing contact records with overlay addresses pulled from /meta or from fetched contacts pages.

## Decisions

### Decision: Auto-generated by daemon as default; operator override by placing their own contact.mu

**Status:** decided
**Rationale:** Daemon generates ~/.styrene/pages/contact.mu at startup from identity config + active overlay addresses (same pattern as existing index page generation). If operator has placed their own contact.mu (detected by modification time or a managed: false front-matter flag), daemon skips overwrite. Default auto-generation ensures every node has a working contacts page without setup — critical for i2p-address-book population and cross-topology discovery. Requiring operator authorship would mean most nodes have no page, defeating the feature.

### Decision: Fetching /page/contact.mu enriches the local contact record passively on explicit page load — not background crawl

**Status:** decided
**Rationale:** When the operator fetches a peer's /page/contact.mu in the Pages tab, overlay addresses (b32, ygg, web_url) found in the page are written to that peer's contact record. Same enrichment path as /meta DirectLink — the contacts page is the human-readable version of the same data. Background crawling all peers' contacts pages is an I2P bandwidth concern and a privacy concern (unsolicited fetches). Trigger is always explicit operator page load, never a background job. Enrichment is idempotent: re-fetching updates existing fields, doesn't create duplicates.
