# Cross-Language Wire Protocol Roundtrip Tests

## Overview

Build a cross-language roundtrip test suite that encodes every Styrene message type in Python (styrene_wire.py), decodes in Rust (styrene-mesh/wire.rs), and vice versa. Catches schema drift between the two implementations without introducing a shared IDL or changing the serialization format.\n\nScope:\n- Generate canonical test vectors from Python for all ~50 message types\n- Rust test that deserialises each vector and re-serialises to byte-identical output\n- Python test that deserialises Rust-generated vectors\n- CI job that runs both sides and fails on any mismatch\n- Test vectors checked into repo as fixtures (JSON or binary files)\n\nThis is the pragmatic first step before a shared schema codegen (option 1 from the IDL assessment). If drift becomes frequent, graduate to a TOML/YAML schema with codegen.

## Decisions

### Decision: Test vectors live in styrene-rs under tests/fixtures/wire/ — generated by styrened tooling, consumed by both sides

**Status:** decided
**Rationale:** Vectors live where the primary consumer (Rust tests) can find them without cross-repo fetching. A Python generator script in styrened/tools/generate_wire_vectors.py produces the vectors; the checked-in output lives in styrene-rs. styrened's reverse-direction tests reference the fixtures path via a submodule or pinned git ref. Same placement logic as the wire IDL schema: generated artifacts live with the implementation that owns the canonical wire format definition (styrene-rs/styrene-mesh).

### Decision: Both binary blobs and JSON sidecars: binary for byte-exactness assertion, JSON for human-readable debugging and hand-authoring

**Status:** decided
**Rationale:** Binary .bin files are the ground truth for roundtrip tests — Rust and Python decoders must produce byte-identical output. JSON .json sidecars (same basename) describe field values and serve as human-readable source for debugging drift and hand-authoring new test cases without running the Python generator. The Python generator produces both from the same message definition. Binary-only makes drift debugging opaque; JSON-only loses the byte-exactness guarantee that is the whole point of cross-language tests.

### Decision: styrene-rs CI owns the cross-language matrix job — generates fresh vectors via Python, tests both Rust decode and Python decode in one job

**Status:** decided
**Rationale:** styrene-rs already owns cargo test for the wire protocol. The cross-language job extends this: (1) runs Python generator to produce fresh vectors, (2) Rust roundtrip tests decode and re-encode to byte-identical output, (3) Python decoder tests run against Rust-generated vectors. Single job, single ownership, one place to investigate failures. styrened CI verifies its own encode/decode consistency independently but does not own the cross-language matrix. Requires only a Python dev dependency in styrene-rs CI (already present for styrene-native PyO3 build tooling).
